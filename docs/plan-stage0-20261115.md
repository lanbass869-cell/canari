# Stage 0 result and the revised plan (2026-11-15)

Hypothesis under test: "MCP has no protocol-level channel for a third-party
verifiable claim about a tool, so filling it is an open technical position."

**Result: false.** The channel is a crowded proposal space, and the real
blocker is process, not protocol.

---

## 2. Why the well-developed ones were closed

Neither was closed on technical merit.

#3140 (17 comments, JWS-signed capability manifest, trust label block, rug-pull
change semantics, a 35/35 conformance PoC by an independent commenter) was
closed 2026-09-22 by maintainer `localden`:

> "The MCP Maintainers and Core Maintainers met last week, and one of the changes
> we're making is that **every new SEP should be developed with the help of a
> Working Group**. That way each proposal has a group of interested folks behind
> it before it comes up for review. I'm going to close this one out for now so
> it can go through that path."

#2809 (ATSA, 14 comments) was closed 2026-11-08 by `dsp-ant`:

> "For SEPs to be accepted, they will have to go through the relevant group, in
> this case the **Security Interest Group**."

Both point at the same gate: a Working Group. Not a spec argument.

## 3. The constraint that matters most for this project

In the #2809 thread, `localden` wrote:

> "this is usually triggered if you are using **clearly AI-written responses (or
> AI-driven responses)** in any of the Discord channels."

The contributor being discussed had their access restricted. This is an
operational fact, not a rumour: agent-authored community posts are detected and
penalised. It means **this agent must not post in MCP community channels on the
user's behalf**, and any SEP draft it produces has to be something the human
presents as their own work, which is fine only if the human actually understands
and owns it.

That changes the division of labour: I can produce artefacts and evidence; the
human has to be the participant.

## 4. What is genuinely open, and it is narrow

In the #3140 discussion, `Tetsurohhori` raised the objection that survived
everyone's answers:

> "signatures and content hashes attest to **what was declared at signing
> time**. They do not, by themselves, constrain what the implementation does
> afterward. In static audits of MCP servers, most findings are
> manifest/capability mismatches — undeclared network, write, subprocess, or env
> reach — where the declared surface stays plausible while code drifts."

That is the declared-versus-observed gap, and #3140's trust labels do not close
it.

## 5. There is already a draft that does exactly this, and it says it needs a second implementation

`draft-templeman-scitt-measurement-capsule-01`, dated 27 October 2026, expires
2027-04-30, defines a "measurement capsule":

> "a small, deterministic JSON record in which a party that is **neither the
> subject of a claim nor a participant in the action it concerns** records **what
> the subject declared, what the measuring party observed, and the difference
> between the two**. A capsule carries digests of its evidence, a measurement
> state in which **"could not be checked" is a first-class outcome**, and no
> decision, approval or authorisation. Capsules are identified by the SHA-256 of
> their JCS serialisation and **batched under an RFC 9162 Merkle Tree Hash**."

It states its comparison kinds explicitly include MCP:

> "They compare: an MCP endpoint's registry, mcp.json, server-card and
> payment-manifest declarations with its live initializ[ation]…"

And it states why it is still Experimental:

> "The document is Experimental because its requirements on decision fields and
> UNCHECKABLE … have **not been shown useful by more than one implementation**."
>
> "The checker is written by the same organisation, so it is **not the
> independent implementation the experiment asks for**."

Published artefacts (verified reachable this session):

- Draft text: `ietf.org/archive/id/draft-templeman-scitt-measurement-capsule-01.txt`
- Vectors and generators: `github.com/CSOAI-ORG/councilof-ai/tree/master/docs/ietf/measurement-capsule-01/test-vectors`
  - `vectors.json` 24,356 bytes; `gen_vectors.py` 16,452; `check_vectors.py` 11,980
  - contents: `V1_capsules` (5), `V2_batch` (7), `V3_cose_sign1_attached` (5),
    `V4_cose_hash_envelope` (6), plus `N_controls`

A sample capsule from the published vectors:

```json
{
 "capsule_id": "790c6908…ae4d",
 "kind": "measurement.contract_parity",
 "claim": {"statement": "the protocol version a registry entry declares for this endpoint equals the version the endpoint returns from initialize"},
 "declared": {"surface": "registry", "protocol_version": "2025-06-18"},
 "observed": {"exchange": "initialize", "protocol_version": "2025-11-25"},
 "differential": {"differs": ["protocol_version"]},
 "measurement_state": "INCONSISTENT",
 "sources": {"registry_entry": "bc012a01…d387", "initialize_response": "62e37c18…a07"},
 "limitations": ["the registry entry and the endpoint were read 40 seconds apart from one location"],
 "authority_state": "NONE: measurement only; this capsule grants and records no execution authority",
 "schema": "csoai.measurement-capsule/0.2"
}
```

Note what this format encodes that Canari's current verdict does not:

- the declaration and the observation as separate, hashed things
- an explicit differential naming the differing fields
- `limitations` as a required-ish field
- `measurement_state: INCONSISTENT` instead of "fail"
- `authority_state: NONE` — a measurement grants nothing
- `capsule_id` = SHA-256 of the JCS serialisation, so the identifier is the
  content

## 6. Why this is the right target for Canari

| Requirement in the draft | Canari today |
|---|---|
| issuer is neither subject nor participant | yes |
| records declared and observed separately | partially (subject + checks, but no explicit declared surface) |
| explicit differential | no |
| `UNCHECKABLE` never becomes pass/fail | **yes** — this is exactly the bug we fixed on 2026-08-… when gitleaks severity was missing and defaulted to medium; we changed it to `unknown` + fail-closed |
| capsule_id = SHA-256 of JCS | no (we hash a DSSE payload) |
| batched under an RFC 9162 Merkle Tree Hash | **yes** — that is the log built today |
| second independent implementation | that is what is being asked for |

Five of seven requirements are already met or nearly met. The work is to emit
capsules instead of (or alongside) verdicts, and to pass the published vectors.

## 7. Revised plan

### Stage A — conformance against the published vectors (3 to 5 days)

1. Implement the capsule serializer: JCS canonical JSON, `capsule_id` =
   SHA-256(JCS with `capsule_id` excluded), and the batch over an RFC 9162 MTH.
2. Run the published `vectors.json` through it. Both direction: parse their
   capsules and reproduce their `capsule_id`; and produce our own and compare
   against their `check_vectors.py`.
3. Publish a conformance report: which vectors pass, which fail, and every
   disagreement with a minimal reproduction.

**Acceptance**: `V1..V4` and `N_controls` all pass, and the report is public.
**Falsification**: if the draft's own vectors are internally inconsistent for
anything Canari can produce, that is a finding for the draft author, not
something to paper over.

### Stage B — emit real capsules for real MCP servers (1 week)

Take the existing scan pipeline and emit capsules whose `declared` is the
registry/server.json surface and whose `observed` is what we actually got from
`initialize` + `tools/list`. That is precisely the comparison the draft names.

**Acceptance**: for N real servers, a stranger can take one capsule, its two
source digests, and verify the differential by hand.

### Stage C — write to the draft author, not to the working group (1 day)

Send the conformance report and the divergences to the draft's author. The
draft explicitly says it needs a second implementation; that makes this a
welcome message rather than a proposal competing for sponsor attention. It is
also a GitHub/email channel, not Discord, so the AI-posting problem does not
arise.

### Stage D — only then consider MCP process

If the capsule work lands, the natural next step is to reply in the open SEP
#1913 thread with a concrete artefact (a capsule for a real server plus its
verification), not with a proposal. **That comment must be written and posted by
the human.**

## 8. What this does and does not buy

Buys: a defensible technical position ("the second implementation of a SCITT
profile that the draft itself says it lacks"), plus an artefact that answers the
strongest objection raised in the MCP SEP threads.

Does not buy: a moat. Somebody else can be implementation #3 tomorrow. What
compounds is still only history and witnesses. But this is the first option
found in this session that is simultaneously (a) not already done as a
product, (b) explicitly requested by the standard's author, and (c) mostly
already built in this repository.
