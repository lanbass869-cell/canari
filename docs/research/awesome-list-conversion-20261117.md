# awesome-list 到底带不带量？—— 一次实测（2026-11-17）

## 0. 结论先行

**几乎不带。**

在最大的 MCP awesome list（`punkpeye/awesome-mcp-servers`，约 96K star，已合并 "Add …" PR 共 **5,189** 个）里，随机抽 **294 个"合并已满 30 天"的条目**：

| 指标 | 数值 |
|---|---|
| star 中位数 | **1** |
| star 均值 | 52.7（被一个 2013 年的老项目拉到 6,571，剔除后均值 15.3） |
| **0 star** | 97 个（**33%**） |
| ≤1 star | 153 个（52%） |
| **≤5 star** | 211 个（**72%**） |
| ≤10 star | 234 个（80%） |
| ≤100 star | 282 个（96%） |

也就是说：**被这个榜收录，换来的中位收益是 1 个 star。三分之一的条目至今是 0。**

## 1. 对照组：被拒的条目，star 一样低

同一时间窗内**关闭但未合并**的 PR，随机抽 81 个可解析仓库：

| 组 | n | 中位 | 均值 | 0 star 占比 |
|---|---|---|---|---|
| 合并 | 294 | 1.0 | 52.7 | 33% |
| 被拒 | 81 | 0.0 | 43.4 | 52% |

Mann-Whitney U = 14,069.5，**z = 2.50**（p ≈ 0.012）。

技术上"显著"，但**效应量小到没有意义**：中位数差 1 个 star。而且方向上有明显反向因果——**项目是因为已经有点名气才被收录，不是因为被收录才有名**：样本里 star 最高的 `kucherenko/jscpd`（6,571）是 **2013 年**创建的项目，2026-09-21 才被加进榜。

## 2. 这条结论能解释什么

- **不是"我们推广没做好"**：294 个做对了流程、通过了审核、真的被合并的项目，中位数是 1 个 star。
- **不是"我们的材料不够硬"**：榜本身 96K star，但 star 不会顺着链接流下去。
- **是渠道本身**：awesome list 是**发现索引**，不是**分发渠道**。它服务于"已经知道自己要找什么"的人；而我们的目标用户（不知道自己要找第三方账本的人）根本不会去搜。

## 3. 方法

- 数据源：GitHub Search API（`repo:punkpeye/awesome-mcp-servers is:pr is:merged closed:<2026-10-10`），翻 10 页共 1,000 条，得到 688 个唯一被增仓库；随机抽 300，取到 294 个可读仓库信息。
- 对照组：同一查询改 `is:unmerged`，翻 3 页得 171 个唯一仓库，随机抽 90 个，81 个可读。
- 时间：2026-11-17（UTC+8 下午）。star 数为抓取当刻的 `stargazers_count`。
- 统计：Mann-Whitney U，正态近似（未做连续性校正）。

## 4. 限制（必须一起读）

1. **这是横截面，不是面板**。我拿不到第三方仓库的逐星时间线：GitHub 的 `/repos/{o}/{r}/stargazers` 对非本账号拥有的仓库一律返回 **404**（实测 `cli/cli`、`octocat/Hello-World` 都是 404，自己的仓库 200）。所以**不能**做"上榜前 30 天 vs 后 30 天"的严格前后对比。
2. **合并 vs 被拒的差异有混杂**：被收录的项目可能在质量/合规上更接近"可分发"，但也可能是本来就更活跃。混杂方向不确定。
3. **样本是中位数 1 的分布**，均值被长尾严重拉动，任何"平均值"都必须和中位数一起报。
4. **只测了一个榜**（虽然是最大的那个）。TensorBlock / yzfly / awesome-claude-code 等未测。

## 5. 可执行的推论

既然榜单不带来流量，那么"多投榜"的期望收益接近于零——这与我们自己的实测一致：该账号已投 32 个 awesome PR（7 合并 25 未合），Canari 至今 **0 star**。

要点从"被收录"转向**"被使用"**：唯一能绕开"用户得先知道要搜什么"的路径，是**塞进用户已经天天在用的东西里**（客户端 config / 一个真实被依赖的仓库的依赖 / 某个 issue 里已经有人在喊的需求）。
