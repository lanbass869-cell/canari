# 深度调研：无客户前提下，这个项目还能不能立住

日期：2026-11-15　性质：调研报告（先于方案）

## 0. 结论（先说结论）

能立住，但**不在"技术很难"这一层**，而在**标准位、唯一运营者、时间语料、离线可验证**这四层叠加。
调研到的最关键一条事实：IETF 的 SCITT 工作组已经把"可验证供应链透明日志"标准化到草案阶段，但**至今没有面向 AI 智能体组件（MCP）的 profile**。这是唯一还空着、且不需要任何客户就能占的位置。

## 1. 调研方法与范围

用 GitHub 官方接口逐个读一手材料（仓库、README、issue 正文与评论），不引用二手报道。检索方向与命中：

| 方向 | 检索 | 一手命中 |
|---|---|---|

## 2. 五个关键事实（每条有出处）

**事实一：透明日志这件事有正式标准组织在做，而且还在推进中。**
IETF SCITT 工作组仓库在 2026-10 仍有提交；文档包括架构草案、Transparency Service REST API（SCRAPI）、CCF 收据 profile。这说明"可验证透明日志"是被认可的正式方向，不是我们臆想。

**事实二：标准里没有 AI 组件的位置。**
SCITT 的七个子仓库里，软件用例草案停在 2023 年且无人维护，没有 AI/ML/MCP 相关 profile。也就是说：标准框架有了，但"AI 智能体组件该签什么、该记什么"没人写。

**事实三：已经有人把 Rekor 用到了 MCP 上，但明确做不到离线验证。**
Anchor（intelligent-ears/Anchor，2026-08-30 建，12★）做工具 schema 的防篡改：JCS 规范化、in-toto 声明、cosign 无密钥签名、提交公开 Rekor、哈希链、分叉检测、身份轮换。
它的 Known limitations 原文列了三条要害：不支持基于密钥的签名、不支持自建日志实例、**不支持离线/气隙验证**；并写明自己是原型、未做安全评审、predicate 未标准化。
还有一条它踩到的坑值得记：Rekor 的 dsse 类条目只存哈希不存载荷，所以"只靠公开日志重建历史"这条路它没走通。

**事实四：每日证据语料已经在跑，但没人给它签名。**
registry#1715 里两家独立项目按统一字段 {entry, version, checked_at, check, state, evidence} 每日导出，CC BY 4.0；mcpcost 的索引里带 bytes 与 sha256。这些是普通 JSON 文件，没有任何签名或时间戳证明。

**事实五：扫描器那一层已被大厂占满。**
NVIDIA 25945★、腾讯 7502★、Snyk 3239★。我们不在这层竞争。

## 3. 由此推出的：能用与不能用的壁垒

**不能用的两类：**
- "密码学很难"——不成立。RFC 9162 与 SCITT 已经把 Merkle 包含/一致性证明写成规范，还有现成实现（scitt-cose 明确写着严格实现 RFC9162_SHA256）。写这个不是壁垒。
- "功能更多"——不成立。同赛道每一小块都有专人。

**能用的四类：**
1. **标准位**：SCITT 缺 AI 组件 profile，谁先写出被讨论的 profile，谁定义"AI 组件该签什么"。
2. **唯一运营者**：Anchor 用第三方公共日志（Rekor），受制于它的条目类型；我们可以自建日志、自己签树头，不受制。
3. **时间语料**：每天追加一次，后来者补不出过去。
4. **离线可验证**：Anchor 明说不支持；气隙/内网场景只有这条路。

## 4. 推荐打法

**两条腿同时走，都不依赖客户。**

**腿一：写 SCITT 的 AI 组件 profile（标准位）。**
内容不是空谈，是给出可检验的定义：
- Signed Statement 的 subject 是什么（组件标识 + 制品 sha256 + 版本）；
- predicate 里必须有哪些字段（判定结论、检查项、上游工具身份、证据引用）；
- 什么情况必须记为 unsupported（例如"哈希由生产者公布、本服务未重算"）；
- 收据（receipt）与树头的格式；
- 一组跨实现的测试向量。
产出形式：一份 Internet-Draft 风格的文档，提交给 SCITT 工作组邮件列表/仓库讨论；同时以仓库文档形式公开，任何人都能照着实现。

**腿二：跑起来那本日志（唯一运营者 + 时间语料）。**
- 每天把外部证据导出做成签名记录（已实现）；
- 追加进 Merkle 树，产出签名树头；
- 提供包含证明与一致性证明，**全部可离线验证**；
- 树头每天公开一次，并请外部维护者各自留档（gossip 起点）。

## 5. 为什么零客户也能推进（自证清单）

- 树头序列本身就是产出：第 1 天、第 2 天……第 N 天，任何人可核。
- 反向测试可自证：篡改任一历史记录、或用缩短的树头冒充，验证器必须拒绝并说明是包含性还是一致性失败。
- 跨实现可自证：两套独立实现跑同一组向量，根哈希必须逐字节一致。
- 标准位可自证：profile 文档被工作组仓库引用/讨论即为进展，不需要用户。

## 6. 什么情况下这条路也不成立（预先写死反证条件）

1. 若 SCITT 在半年内推出 AI/ML profile，且由大厂主导——标准位没了，只剩运营者。
2. 若 Anchor 补上离线验证并自建日志——差异化消失。
3. 若两家每日证据源停更或改格式且无人替代——语料断流，日志变空转。
4. 若我们连续 30 天无法稳定追加（网络/环境问题）——时间语料这条壁垒自己就断了。

## 7. 第一周要交付的东西

1. Merkle 核心 + 对抗性测试 + 跨语言测试向量（JSON）。
2. 每日追加脚本 + 签名树头。
3. 离线验证器（只依赖公钥与记录包）。
4. profile 文档初稿（面向 SCITT 讨论）。
