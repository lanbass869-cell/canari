# 无客户也能立住的护城河：方案与依据

日期：2026-11-15
状态：提案（未实施）

## 一、结论

在没有客户的前提下，能立住的护城河只有四类：**时间积累、离线可验证性、标准定义权、实现难度**。
前三条不依赖任何人使用；第四条只依赖自己写对。其余任何"功能更多""界面更好"都不构成壁垒。

本方案选择把四者叠在同一个东西上：**一个完全离线可验证的、仅追加的组件证据日志**。

## 二、为什么是这四条（不是拍脑袋）

1. 时间无法回补。今天开始逐日记录的语料，别人一年后开始也补不出这一年。这类护城河不需要客户，只需要坚持。
2. 离线可验证是真实缺口。同类项目 Anchor（intelligent-ears/Anchor，2026-08-30 建）在 README 的 Known limitations 里逐条写明：不支持基于密钥的签名、不支持自建日志实例、**不支持离线/气隙验证**。企业内网、航空、军工场景恰恰只有这一种验证方式。
3. 标准定义权：谁先发布规范化规则、记录格式和跨实现测试向量，后来者就得对齐你。这个圈子里已经有先例——工具接口指纹那一线，几方已经互相约定"逐字节一致"的向量集。
4. 实现难度：Merkle 包含证明与一致性证明容易写错（边界、空树、末节点奇数提升），写错时"看起来能验过"是最危险的失败模式。写对并在测试里钉死，本身就是技术资产。

## 三、已被占的部分（必须先承认）

- 工具接口指纹 + 透明日志：Anchor 已在做，用 Sigstore 无密钥签名提交公开 Rekor 日志，含哈希链、分叉检测、身份轮换、按身份重建历史。仍是原型，作者自己写了"未做安全评审、predicate 未标准化"。
- 每日证据导出：两家独立项目已在跑（mcpcost、ProtocolProbe），按 {entry, version, checked_at, check, state, evidence} 约定格式，CC BY 4.0，每日更新。
- 包的完整哈希字段：registry#1783 有正式提案与全量测算；客户端侧已有 CapLock。
- 扫描器：NVIDIA SkillSpector 约 2.6 万星、腾讯 AI-Infra-Guard 约 7500 星、Snyk agent-scan 约 3200 星。

所以我们不做"再加一个扫描器""再做一个指纹服务"。

## 四、我们要做的东西

**一句话：把"某天某份证据文件长什么样"逐日钉进一个可离线证明未被改写过的日志里。**

具体形态：

1. 每天把外部发布的证据导出（索引 + 数据文件的 sha256 + 生产者身份 + 条目统计）转成一条签名记录（已实现：canari/evidence_notary.py）。
2. 把这些记录按日期追加进一棵 Merkle 树。每追加一批，产生一个签名过的树头（tree head）：树大小 + 根哈希 + 时间。
3. 任何人拿到任意一条记录，可以离线验证：
   - 记录本身的签名；
   - 它在这棵树里的包含证明（inclusion proof）；
   - 当前树头与他自己保存的旧树头之间的一致性证明（consistency proof），从而确认"历史只增未改"。
4. 树头用 gossip 方式散步：写进 README、写进 GitHub Release 说明、发给对方项目维护者。两个互不信任的观察者各自保存过的树头互相矛盾，就证明有人分叉了日志。
5. 全部产物开源、可下载、可离线校验；不依赖任何在线服务。

## 五、为什么这构成壁垒（逐条对应）

- 时间：树越长，包含证明越有价值；后进者无法伪造 2026 年 11 月的历史。
- 离线：同类项目明说不支持；气隙环境只有我们能验。
- 标准：我们发布 Merkle 规范 + 向量集，别人要对齐。
- 难度：证明代码写错会"验过假记录"，必须有对抗性测试。

## 六、里程碑（按可验证产出排，不按"看起来做完"排）

第一阶段（约 3 天）：Merkle 核心
- 实现叶子/节点哈希域分离、包含证明生成与校验、一致性证明生成与校验。
- 对抗性测试：空树、单叶、奇偶提升、篡改任一叶、篡改证明路径、旧树头非前缀。
- 产出：一组跨语言可用的测试向量（JSON），每条含输入、期望根、期望证明、期望结果。

第二阶段（约 2 天）：每日追加与树头
- 每日 cron：拉取外部证据索引 → 生成存证 → 追加进树 → 产出树头并签名。
- 产出：tree-head.json 历史序列 + 当日记录包。

第三阶段（约 2 天）：离线验证器与页面
- 只需一个公钥 + 记录包，离线完成三步验证。
- 页面公开树大小、根哈希、最近一次追加时间，以及历史树头的哈希链。

第四阶段（持续）：语料与播报
- 每天追加一次，永不回补。
- 把树头贴给对方项目维护者与相关讨论串，请他们各自留档（gossip 的起点）。

## 七、如何自证（不需要客户）

- 反向测试：故意篡改一条历史记录、故意给一个旧树头配一个"缩短"的新树头，验证器必须拒绝，且错误信息要点明是包含性失败还是一致性失败。
- 跨实现：用第二套独立实现（不同语言/不同人写）跑同一组向量，根哈希必须逐字节一致。
- 第三方留档：请外部维护者保存树头；他们持有的旧树头就是我们无法篡改历史的证明。

## 八、风险与边界（写在前面）

- 这条路的产出是"基础设施"，不是爆款产品；不会带来几千星。
- 外部数据源可能停更或改变格式，需要适配层与失败告警。
- 我们仍不能证明"数据内容为真"，只能证明"这份数据在某天以这个哈希被发布过，且此后历史未被改写"。记录里必须一直写明这一点（现有实现已把 L2.1 标为 unsupported 并注明未重算）。
- 不发公开分叉、不做不可撤销的公开提交，除非明确知道后果。
