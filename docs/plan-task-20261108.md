# Canari 任务方案 v2 (2026-11-08) - 基于证据级调研 v4

> 定位一句话：Canari 是跨 registry 的「判定层」——把 npm/PyPI 的原生身份证明（provenance/PEP 740）、
> 扫描器的深度结论、dsh.so 的 L5 安装实测，统一成签名、可离线验证、带 supersession 链的判定工件，
> 并提供同源失效传播与消费端安装门禁。
> 它不做身份证明（registry 已做），不做深度扫描（竞品已做），不做运行时（SIGIL/germline 已做）。

## 一、调研结论回放（方案的依据，全部实测）

1. mcpcheckup（活产品）：DSSE+Ed25519+离线验证器+密钥吊销+基线漂移对比+history API，
   官方 MCP Registry 收录。它只覆盖远端 MCP server，无跨 registry、无 supersession、无传播、无安装门禁。
2. SIGIL（论文 2605.05274）：链上 skill registry + DAO 审计 + 调用时验证，1079 真实技能评测。
   无跨 registry、无便携离线验证（链上门槛）。
3. agtmls（仓库）：签名 skill registry + 吊销 advisory feed（verify 退出码 6）+ 安装 lockfile。
   只服务自己的 registry。
4. 2601.23132：manifest 签名 + append-only transparency log + 吊销，MCP 管线内。非跨 registry。
5. 2608.18180：34,005 包跨 4 生态的可验证构建测量（npm 62 次/PyPI 47 次提及）。
   测的是「能否独立重建」，不是判定账本，零 supersession。
6. npm provenance 实测：top-30 包 60% 有 Sigstore provenance；express@5.3.0 的 bundle 是
   DSSE v0.1（publicKey hint + tlog）+ v1（certificate + tlog）双条目。
   sigstore-python 4.5.1 可装可 import，但其 Bundle 模型要求证书链——npm v0.1 的
   publicKey-hint 路径需要自己实现 DSSE 验证或标记为「存在性信号」。
7. PyPI 实测：0/30 顶级包、0/40 新上传、0/10 Trusted Publisher 知名包带 attestation。
   pypi-attestations 0.0.31（PyPA 官方库）存在，PEP 740 转换/验证可直接用。
8. dsh.so：10,195 插件 100% install-verified（抽样 12 个，10 个 L5 记录新鲜度 11-04~11-07），
   per-plugin 接口返回 commitSha + counts(critical/warning/info) + rulesChecked=31，CC-BY-4.0。
9. 扫描器格局：repo-forensics 1,138 个 re.compile（最深开源），cisco skill-scanner ~90 规则，
   SkillWard 52，agentshield 39，SkillSpector 20 条 YARA（README 虚标 71）。
10. 2611.01976 的原话（论文引言级论据）：「hashes and attestations certify WHICH code runs,
    never WHAT it does」——这是 Canari 判定层存在的根本理由，直接引用。

## 三、P0 详设

### T1 论文（题目暂定）
"Verdict Attestations: A Cross-Registry, Offline-Verifiable Ledger for AI Agent Component Supply Chains"

结构：
1. Intro：2611.01976 工具更新缺口（97.6% ASR）+ 2611.06585「签名不等于良性」+ 2611.02527 90% 破坏性工具无确认。缺口：身份证明（provenance）与深度扫描之间存在「判定层」空白，且现有账本各自为战（mcpcheckup 只管远端 MCP，SIGIL 链上门槛，agtmls 单 registry）。
2. Threat model：registry 身份 ≠ 组件判定；stable name + mutable content（2609.14119: 40.6% 多版本变更、4.2% 端点劫持）。
3. 格式：DSSE + Ed25519；supersession 链语义（supersedes 指针、不可删除、冲突检测）；bi-temporal 时间轴；失败透明（dead_letter 计数公开）。
4. 系统：M0-M2 架构图；四 registry 适配器；L0-L3 分层（编排查现成扫描器，不自研引擎——引 repo-forensics 1138 规则作 L3 参考实现）。
5. 实验：
   a. 覆盖：294 attestation（npm 100/PyPI 94/MCP 100）+ schema 完整性 99.6%；
   b. 漂移案例：复用 Zenodo 21798111 面板选 top-5% 漂移 server，展示判定链随时间演化；
   c. 原生摄入：express 双 bundle + PyPI 空白率 0/40 的对比表；
   d. 传播：同作者失效传播 5 个测试用例；
   e. 失败诚实性：dead_letter 计数公开 vs 竞品通过率注水（score.py 四维卡）。
6. Related work 表：mcpcheckup / SIGIL / agtmls / 23132 / 18180 / SkillSpector / cisco / snyk / trustcheck / ATSA(2605.24248) / ProbeID / MCP-Eco / 89天漂移 / Same Name。每家一行「它做了/它没做」。
7. 局限：扫描深度 0（编排定位）、单签名者信任根、MCP 计数是下限。

写法纪律：不用特殊 Unicode；每个数字带口径；诚实声明 distortion（MemTether 纪律）。

### T2/T3 原生摄入（决定 Canari 是「聚合点」还是「又一个签名格式」）
- npm：GET registry.npmjs.org/{pkg} -> dist.attestations {url, provenance}；
  下载 bundle（实测 express@5.3.0 = 14.5KB，双条目：publish v0.1 + slsa v1）；
  v1 条目（certificate + tlogEntries）走 sigstore-python 4.5.1 Verifier.production()；
  v0.1 条目（publicKey hint）标注 PROVENANCE_PRESENT（存在性），不做假验证。
  Canari 判定工件新增字段：native_provenance: {present, predicate_types, verified: bool, verifier: "sigstore-python/4.5.1"}。
- PyPI：pypi-attestations 0.0.31 把 PEP 740 对象转 Sigstore Bundle -> 同上验证。
  由于实测 0/40 覆盖率，PyPI 摄入主要为未来准备好 + 论文里展示空白（这本身就是 finding）。
- 验收：npm 侧真实验证 PASS 用例 >=1（express）+ 伪造篡改 FAIL 用例 >=1；PyPI 侧转换 PASS + 无 attestation 时的诚实记录。

## 五、明确不做（scope discipline，来自调研教训）
- 不做平台/网站/账号体系（禁区）。
- 不做新签名协议（DSSE 够用，ATSA 已占坑）。
- 不自研扫描引擎（repo-forensics 1138 规则免费拿，编排它）。
- 不做运行时（SIGIL/germline/ACLE 已占）。
- 不宣称官方背书（dsh.so 明确 non-affiliated；MCP registry 无 attestation 字段）。
- 不在核心链路加 LLM（架构守卫，无例外）。
