## 一、P0：工程质量提升（本周，11-10 至 11-14）

### D1: NFC 归一化（2h）

mcpcheckup 用 NFC-JCS 规范化防止 Unicode 归一化差异导致假 drift。
Canari 的 `json.dumps(sort_keys=True)` 没有做 NFC 归一化。

**实现：**
- 在 `signing.py` 的 `sign_attestation()` 里，序列化前对每���字符串值做 `unicodedata.normalize('NFC', s)`
- 在 `verify_cli.py` 的 `_independent_verify()` 里同样做 NFC
- schema v0.1 的 canonicalization 字段从隐式改为显式声明 `"nfc-json/v1"`

**验收：**
- 测试：`"caf\u00e9"` 和 `"cafe\u0301"` 归一化后产生相同的 payload hash
- 现有 63 个测试不破坏

**文件：** signing.py, verify_cli.py
**新测试：** test_signing.py 加 2 条（NFC round-trip + 碰撞检测）

### D2: digest ��缀格式（0.5h）

mcpcheckup 的 digest 输出 `"sha256:<64 hex>"`，Canari 输出裸 hex。
加前缀让消费者可以识别算法。

**实现：**
- `verify_cli.py` 的 payload sha256 输出改为 `"sha256:<hex>"`
- `_independent_verify()` 的返回值同理

**验收：** verify_cli 输出包含 `sha256:` 前缀

### D3: guardsAgainst 字段（1h）

mcpcheckup 的每个 fixture 都有 `guardsAgainst` 字段说明防止的 bug 和来源。
Canari 的测试没有。

**实现：**
- 在每个 test 文件的 class docstring 或模块 docstring 里加 `GUARDS_AGAINST` 变量
- 内容：这个测试防止的具体 bug / 边界条件 / 来源

**验收：** 每个 test 文件的顶部有 GUARDS_AGAINST 注释

### D4: 攻击语料（4h）

mcpcheckup 的 `rule_eval.rs` 有 77 个良性 + 手工恶意的语料，量化规则质量。
Canari 的 credential_shapes() 有 6 条规则但没有测试语料。

**实现：**
- `tests/fixtures/credential_corpus.json`：50 个良性字符串 + 50 个恶意字符串
- 每条标注 `origin`（npm/PyPI/GitHub/手工构造）和 `expected`（clean/detected + 规则名）
- 测试：对整个语料运行 `credential_shapes()`，统计 FP 率和 FN 率

**验收：**
- FP 率 < 5%（50 个良性中误报 ≤ 2 条）
- FN 率 < 10%（50 个恶意中漏报 ≤ 5 条）
- 输出质量报告：`"FP: 2/50 (4%) FN: 3/50 (6%)"`

### D5: run_weekly.py 验证运行（2h）

上次调度任务失败（LastTaskResult=1）。当前代码 import 链已验证通过。
但需要完整跑一次 deep_scan_with_metadata 确认端到端无崩溃。

**实现：**

- 检查 out/weekly_scan.log 是否有输出

- 检查新 bundle 的 signature 是否 PASS

**验收：** weekly_scan.log 有 "completed OK" 行；新 bundle 可验证

### D6: 每周扫描验证 + fixture corpus 接入管线（2h）

用 D4 的攻击语料测试 pipeline 的 credential_shapes() 在真实 attestation 上的表现。

**实现：**

- 如果有命中 → 检查是误报还是真泄漏

**验收：** 243 个 bundle 的 credential_shapes() 结果为空或可解释

## 二、P1：系统完整性（下周，11-17 至 11-21）

### E1: Install gate 完整实现（6h）

当前 `is_gate_passing()` 只检查 verdict。agtmls 的 smoke-install-verify.py 定义了 6 个安全属性。

**实现：**
- `canari/gate.py`（新文件）：
  - `GateDecision` dataclass：ALLOW / BLOCK / REVIEW + reason
  - `evaluate_gate(bundle_path, key_path, policy_name)` → GateDecision
  - 策略引擎（trustcheck 模式）：至少 3 个内置策略（default, strict, release-gate）
  - 每个策略定义：verdict 门槛、freshness 门槛、credential 检测、revocation 检查
- `canari-verify` CLI 加 `--gate` 参数：输出 ALLOW/BLOCK/REVIEW 而不是技术细节

**验收：**
- pass → ALLOW（exit 0）
- pass-with-findings → ALLOW（exit 0，但 stdout 标注 findings）
- fail → BLOCK（exit 1）
- error → BLOCK（exit 1）
- unsupported → BLOCK（exit 1）
- 过期（expires_at < now）→ BLOCK（exit 1，标注 stale）
- 密钥吊销 → BLOCK（exit 1，标注 revoked）
- 策略 strict 下 pass-with-findings → BLOCK

**文件：** canari/gate.py（新）, tests/test_gate.py（新）
**新测试：** ≥10 条

### E2: Supersession 链验证 CLI（3h）

当前 supersedes 指针存在 attestation 里但没有 CLI 验证工具。

**实现：**
- `canari-verify --chain <dir>`：扫描目录内所有 bundle，构建链，检查：
  - 每个 supersedes 指针指向一个存在的 payload digest
  - 无循环引用
  - 链头（无 supersedes）的唯一性
  - 链条完整性（每个 digest 可以追溯到链头）

**验收：** 3-run E2E 测试（round 7 已做过手动验证）在 CLI 中自动通过

### E3: JSON Schema 互拒测试（3h）

mcpcheckup 的 51 个 schema 测试包括：v0.1 样例被 v0.2 拒绝、v0.2 被 v0.3 拒绝。

**实现：**
- 为 Canari 的 schema v0.1 写互拒测试：构造一个含 `native_provenance` 的 payload，确认被不含此字段的旧 schema 拒绝（如果未来有 v0.2）
- 为 `mcp-registry` 枚举值写边界测试：合法的 mcp-registry 条目通过、非法的（空 name）拒绝
- `suite_commit` 格式测试（mcpcheckup 模式）：39 位截断 / 大写 / 64 位 / 非十六进制 / 带前缀 → 全部拒绝

**验收：** ≥10 条新测试

### E4: 差分测试框架（6h）

mcpcheckup 的差分测试：同一输入跑过新旧两个版本 + 独立 oracle，三方必须一致。

**实现（Canari 简化版）：**
- `tests/test_differential.py`：
  - fixture corpus 里选 5 个包
  - 对每个包运行 `build_attestation()` 两次（不同 timestamp）
  - 断言：verdict 相同、checks 的 verdict 集合相同、artifact_sha256 相同
  - 断言：supersedes 指向第一次的 digest
  - 断言：签名验证通过
- 如果未来代码变更导致 verdict 变化 → 测试变红（这就是差分测试的信号）

**验收：** 差分测试通过且有意义（修改 build_attestation 会变红）

### E5: 打开数据集发布（2h）

**实现：**
- 打包 dataset/ 为 zip
- 上传到 GitHub Release（不是 Zenodo——Zenodo 需要 DOI 申请，可以先 GitHub Release）

**验收：** GitHub Release 页面可下载 zip，README 描述准确
