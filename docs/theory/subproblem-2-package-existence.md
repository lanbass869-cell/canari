# 重新选定：注册表发布了装不上的东西（2026-11-19）

## 一、子问题

> **MCP 注册表里有多少条目，会让用户照着它执行安装、然后硬失败？**

载体：`docs/research/package-existence-audit-20261117.md` +
`docs/research/data/package-existence-20261117.csv`（274 条）。

## 二、闸门 1：危害是真的吗 —— **通过（4/4 实测失败）**

不是推断，是刚刚真跑出来的：

| 生态 | 引用 | 状态 | 实际执行 | 结果 |
|---|---|---|---|---|
| npm | `@aiwerk/mcp-server-cal@1.0.6` | package-gone | `npm install --dry-run` | **rc=1**，`npm error 404 ... could not be found` |
| npm | `mcp-server-fetch@0.0.1` | version-absent | `npm install --dry-run` | **rc=1**，`npm error ETARGET notarget No matching version found` |
| pip | `agent-tripwire==0.2.1` | version-absent | `pip download --no-deps` | **rc=1**，`No matching distribution found`（且明确列出 yanked 0.1.1） |
| pip | `aifp` | package-gone | `pip download --no-deps` | **rc=1**，`No matching distribution found` |

**两种失败模式都被实测覆盖**：
- 包整个消失 → npm 404 / pip "no matching distribution"
- 包在但版本不存在 → npm ETARGET / pip "from versions: none"

**这就是那个"所以呢"**：用户不是看到一条可疑元数据，而是**照做就装不上**。

## 三、闸门 2：注册表还在发这些条目吗 —— 通过

- 2026-11-16 快照：274 / 22,526 条引用不可安装（1.22%）
- 2026-11-17 周扫：275 / 22,657（口径同：distinct registry/identifier/version）
- 两次扫描之间数量**没有下降**（274 → 275，因总量增长）
- 今天（11-19）抽样的 4 条**仍然失败**

⇒ **这不是历史遗留，是持续状态。**

## 四、为什么这个子问题值得做（而不是又一个"测了数字"）

三个条件同时满足，而这在今天的候选里是第一次：

| 条件 | 本条 |
|---|---|
| 危害可直接验证 | ✅ 4/4 真实安装失败，有 rc 与错误码 |
| 规模足够 | ✅ 22,526 条引用、274 条坏（1.22%） |
| 机制可归因 | ✅ 注册表发布时校验、事后不复查；上游下架后条目不变 |
| 有明确修复建议 | ✅ 周期复查 + `_meta` 标记，不删条目 |

## 五、三周计划

| 周 | 做什么 | 产出 |
|---|---|---|
| 1 | 把 274 条按"包消失 / 版本消失"分组，各抽 20 条做**真实安装复现** | 复现率（不是抽样推断，是实测覆盖） |
| 2 | 查这些条目的 `_meta` 时间线：它们是何时被发布、何时失效 | 失效延迟分布（发布 → 下架 → 仍被索引） |
| 3 | 写 4 页短文：**注册表把"发布时正确"当成"永久正确"** | 稿子 + 可复现脚本 |

## 六、杀项

1. 若 20 条抽样里复现率 < 80% → 说明我们的判定口径有误，先修口径
2. 若上游在一个月内修掉全部 274 条 → 事件自然结束，降级为 note
3. 若发现"这些条目本来就不该被安装"（例如标记为 deprecated 且有明确提示）→ 危害不成立，关

## 七、与之前六个候选的区别

前面六个：被占 / 平凡 / 要补几个月理论。
这一个：**危害是硬的、数据在自己手里、三周能完、不需要新定理。**

**它不是"新理论"，但它是"能站住的测量"。**

## 八、第 1 周结果：40 条真实复现（2026-11-19）

脚本：`experiments/package_existence_repro/repro.py`，结果：`result.json`。
每组各 20 条，按等间隔从 CSV 中取（不是挑好抓的）。

| 组 | 复现（照做就失败） | 复现率 | 意外装成功 |
|---|---|---|---|
| package-gone | **20 / 20** | **100%** | 0 |
| version-absent | **19 / 20** | **95%** | 1 |

**合计 39/40 = 97.5%**，远高于我设的 80% 杀项阈值。

### 那一个"意外成功"暴露了我们自己的 bug

`local-faiss-mcp` 声明版本 `0.2.0-rc.3`。pip 能装，因为 **PEP 440 会把
`0.2.0-rc.3` 规范化成 `0.2.0rc3`**，而 PyPI 的 `releases` 只认规范形式。
我们的审计直接拿原始字符串去比对，于是把它当成了"版本不存在"。

**这不是被测对象的问题，是我们的测量 bug。** 已经：

1. 查了全部 32 条 PyPI `version-absent`：**7 条**版本字符串与规范形式不同，
   **6 条确认其实可安装**，1 条网络错误未验；
2. 修正 `canari/registry_audit.py`（先规范化再判定）；
3. 新增 `tests/test_pep440_normalisation.py`（5 条）；
4. 在公开报告里加了更正：**274 至少高估 6，修正后至多 268（1.19%）**。

### 这一轮的意义

- **主结论仍然成立**：注册表确实发布了装不上的东西，39/40 真实失败
- **数字变准了**：274 → ≤268
- **第一次在"选定子问题"之后立刻抓到自己的测量错误**——这正是做测量的价值所在

## 九、第 2 周结果：这些坏条目有多老（2026-11-19）

脚本：`experiments/package_existence_repro/staleness.py`。
把 274 条坏引用 join 回 2026-11-18 的注册表快照（66,509 条），取每条记录
`_meta["io.modelcontextprotocol.registry/official"].publishedAt`。

| 指标 | 值 |
|---|---|
| 坏引用 | 274 |
| 匹配到的注册表条目 | **311**（同一条引用可能出现在多个 server 条目里） |
| 条目年龄：最小 | 2.0 天 |
| 条目年龄：p25 | 127.8 天 |
| **条目年龄：中位** | **218.3 天（≈ 7.2 个月）** |
| 条目年龄：p75 | 266.4 天 |
| 条目年龄：p90 | 282.7 天 |
| 条目年龄：最大 | **435.4 天（≈ 14.3 个月）** |
| 年龄 > 30 天 | **301 / 311（96.8%）** |
| 年龄 > 90 天 | **259 / 311（83.3%）** |

按状态拆：

| 状态 | n | 中位年龄 | >90 天占比 |
|---|---|---|---|
| package-gone | 187 | **244.6 天** | 87.2% |
| version-absent | 124 | 192.4 天 | 77.4% |

最老的几条：`mcp-sap-docs@0.3.9`（435.4 天）、`nanobanana-mcp-server@1.0.0`（435.1 天）、
`huoshui-fetch@1.0.0` 等（433.6 天）。

### 这条数字怎么读（必须写清楚）

**条目年龄是"坏掉多久"的上界，不是等号。**
`publishedAt` 是注册表发布该条目的时间；上游消失的时间一定**不早于**它。
所以准确表述是：

> 注册表为一个装不上的引用，**至少**保留了中位 7 个月；其中 83% 超过 90 天。

**不是**"这些安装坏了 7 个月"——是"这些条目存在了 7 个月，而它们现在是坏的"。

### 这条数字为什么重要

它把"注册表不复查"从一句判断变成了一个分布：
**坏条目不会自己消失，它们会一直躺着，中位数已经躺了 7 个月。**

配合第 1 周的 39/40 真实安装失败，这两件事合起来是：

> 注册表在发布时检查一次、之后不再检查；上游消失后，条目继续以"可用"的姿态存在，
> 中位 7 个月，最长 14 个月。用户照着装，97.5% 会硬失败。
