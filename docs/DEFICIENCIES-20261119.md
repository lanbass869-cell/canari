# 深度检测：Canari 的不足

日期：2026-11-19。检测方式：跑覆盖率、读代码、驱动对外接口、把公开数据集当用户数据去消费、查 CI 与计划任务的实际执行记录。

**结论：找到 14 处，其中 2 处会让结论错、3 处会让对外交付物错。已修 3 处，其余列在后面并标明为什么没修。**

---

## 一、会让结论出错的（最严重）

### A1. 端点监控只探前 40 个，且全是 `a` 开头【已修】

`weekly_step` 原来是 `targets(data)[:max_probe]`。注册表按名字排序，所以永远是同一批。

实测这批的顶级域名分布：

| 探测到的 40 个 | 全量 46,325 个 URL |
|---|---|
| `.ae` 17、`.ad` 6、`.africa` 4、`.agency` 4、`.ac` 3、`.academy` 3 | `.com` 17,393、`.dev` 6,190、`.io` 4,858、`.ai` 4,706 |
| `.com` **0**、`.dev` **0**、`.io` **0**、`.ai` **0** | — |

**这和 2026-11-16 那次「84% → 94.78%」是同一个错误**：注册表分页按名字排序，样本与总体系统性错配。那次已经写进 `experiments/mcp_witness/README.md` 当教训，然后新的监控代码又犯了一遍。

修法：预算拆两半——一半给「结论还没定的端点」继续推进 streak，另一半按持久化游标轮换，覆盖到新端点并回绕。

### A2. 端点监控不轮换，同一批永远不变【已修】

即使不看偏差，纯 `[:40]` 也意味着一周又一周探同样 40 个端点，其余 4.6 万个永远不被观测。

修法同上：`EndpointHistory` 新增 `scan_offset`，每次前进并在末尾回绕。三条新测试钉住：两轮不重叠、会回绕覆盖全部、未结论的会被重探。

### A3. 1,578 条「pass」记录自带非 pass 检查，而数据集说明说的是反的

公开数据集里：

| registry | 声称 `verdict=pass` | 其中还带 `skip`/`unsupported`/`fail` 检查 |
|---|---:|---:|
| pypi | 1,798 | **1,415** |
| npm | 1,025 | **163** |
| 合计 | 2,823 | **1,578（55.9%）** |

而 `dataset/README.md` 写着：

> `pass` means our checks found nothing, not that the component is safe.

对那 1,578 条来说，「找到的」是「检查没跑」，不是「什么也没发现」。

`DISCLOSURE-false-pass-20261118.md` 与 README 主文件都披露了这个 bug，**但数据集自己的 README 没有警告**——而数据集才是别人会单独拿走的部分。

**未修**：改写已签发的记录会破坏签名，正确做法是在 `dataset/README.md` 里加一条与主 README 同等的警告，并把快照重刷。这是待办。

### A4. 「变异 kill rate 100%」只对 52 个手挑变异体成立

`scripts/mutations_batch2.py` 定义 52 个变异体，覆盖约 20 类行为（cadence 阈值、typosquat 阈值、signing NFC、gate 策略、drift 判定……）。

分母对比：**52 个变异体 / 5,564 条语句 = 0.93%**（修复本报告所列问题后实测的语句数）。

所以「kill rate 100%」是一个**关于这 52 个变异体的**陈述，不是关于代码库的。它是有效的抽查，不是系统性变异分数。我在之前的总结里把它当成强项讲，讲过头了。

## 二、对外交付物本身有错

### B5. 已发布的 wheel 里版本号是错的【已修】

直接下载 PyPI 上的 `canari_mcp-0.1.4-py3-none-any.whl` 解开看：

```
wheel METADATA      : Version: 0.1.4
canari/__init__.py  : __version__ = "0.1.3"
```

后果：装了 0.1.4 的人问 MCP 服务版本，得到 0.1.3。任何按版本做兼容判断的逻辑都是错的。

根因是两份手维护的版本号——和这个项目抓过无数次的「重复状态必漂」是同一类。

修法：`pyproject.toml` 改成 `dynamic = ["version"]` + `[tool.setuptools.dynamic] version = {attr = "canari.__version__"}`，版本只剩一处；`__init__.py` 升到 0.1.5；四条测试钉住（pyproject 不许有字面 version、必须指向包内、形状合法、MCP server 必须报同一个）。

### B6. 公开数据集 62.9% 已过期

记录带 7 天 `expires_at`。快照是 2026-11-13，今天是 2026-11-19：

| 指标 | 值 |
|---|---:|
| 数据集总记录 | 5,170 |
| 已过期（2026-11-19） | **3,251（62.9%）** |

而 gate 的 `default` 策略 `require_fresh=True`，过期直接 BLOCK。所以**任何拿公开数据集当输入的人，用默认策略会拦掉 62.9% 的组件。**

这不是 bug（过期就该拦），但它意味着：数据集不是「下载即用」的，必须配 `--policy lax` 或者自己先跑一次扫描。README 没说这一层。

### B7. MCP Registry 覆盖 0.29%

store 里 1,437 个组件：

| registry | 覆盖 | 该生态已知规模 | 占比 |
|---|---:|---:|---:|
| mcp-registry | 66 | 22,384 servers | **0.29%** |
| npm | 239 | 数十万 | <0.1% |
| pypi | 611 | 数十万 | <0.1% |
| dsh-registry | 521 | 1 万+ | ~5% |

**gate 对没扫过的组件一律 BLOCK**（fail-closed，正确但等于没用）：`"no attestation for npm:express in store"`。

所以这个 gate 现在的真实定位是「**只对我们扫过的 1,437 个组件有效的一个白名单**」，不是通用的安装检查器。这一点在任何文档里都没说清楚。

## 三、可靠性：会自动失效的部分

### C8. `registry-audit` 的 cron 从未触发

该 workflow 有 `schedule: cron "41 5 * * 1"`（每周一 05:41 UTC）。实际执行记录：**4 次，全部 `workflow_dispatch`（手动）**，时间都在 2026-11-17。

也就是说定时路径**一次都没跑过**。cron 写错、权限不足、commit 失败——任何一种情况都不会被发现，直到 11-23。

### C9. 周扫 7 天 + 记录 7 天过期 = 零余量

`baseline._expiry()` = now + 7 天；`CanariWeeklyScan` = 每周一次。

**任何一次延迟或失败，都会让记录在下次成功之前过期，然后 gate 全线 BLOCK。** 没有缓冲。

实测最近一次成功：`2026-11-16T06:02:18Z`。下一次计划：11-23 06:00。如果 11-23 那次失败，11-24 起所有组件都是 stale。

### C10. 10 条网络测试从不在 CI 跑

`tests/test_native.py` 5 条 + `tests/test_pypi_native.py` 5 条，都标了 `network`，`conftest.py` 里 `CANARI_NETWORK_TESTS` 未设就跳过。

查 `.github/workflows/ci.yml`：**从未设置这个变量**。

所以原生溯源摄取（npm sigstore / PyPI PEP 740）的真实网络路径，CI 里一次都没验证过。上游 API 一改，本地全绿、线上静默坏。

### C11. 原生溯源摄取失败被静默吞掉

`canari/baseline.py:321-324`：

```python
try:
    native_prov = _with_timeout(lambda: native_ingest(name, meta.get("version", "")), 90, None)
except Exception:
    native_prov = None
```

**异常被吞，不记日志、不计数、不进 dead-letter。** 结果是记录里少一个 `native_provenance` 字段，而没有任何人能看出「是本来没有，还是摄取失败了」。

这正是这个项目在别处反复修过的「静默降级」——在这里还留着。

实测后果：npm 原生溯源命中率 52.5%（559/1064），PyPI **0%**（0/2051）。PyPI 的 0 是已知的（模块文档写明 2026-11-08 实测 0/30 有 attestation），但没有监控能区分「上游确实没有」和「我们摄取坏了」。

### C12. `audit_delta` 从未在真实数据上跑过

论文 §7 承诺「2026-12-15 的第二次审计会报告新数值、恢复数和每周流入」。

`docs/audit/package-existence/history/` 里**只有一份快照**（2026-11-17）。所以 `audit_delta` 至今只在合成数据上验证过。

我用一份合成的 after 快照测过它，输出正确（275→270，10 恢复 / 5 新增 / 1.25 每周流入）。功能没错，**但它能否处理真实的两份快照（格式漂移、重复键、版本归一化差异）是未知的**。

## 四、可维护性

### D13. 六个模块覆盖率明显低于总体的 87%

| 模块 | 覆盖率 | 未覆盖的问题 |
|---|---:|---|
| `audit_delta.py` | **56%** | CLI 主函数整段未测（核心 `delta()` 有测） |
| `native.py` | **63%** | 网络路径全在跳过区 |
| `evidence_notary.py` | **69%** | 5 个函数中 4 个分支未测 |
| `mcp_server.py` | **70%** | 对外 MCP 接口，错误分支基本未测 |
| `identity.py` | **71%** | 身份聚类是「同名是不是同一个包」的判据来源 |
| `mcp_probe.py` | **71%** | 探测逻辑，端点监控的核心 |

`identity.py` 和 `mcp_probe.py` 尤其值得注意：这两个模块**输出的是对外结论**（是不是同一个组件 / 端点是不是活着），却被测得最浅。

### D14. 测试代码 9,615 行 > 源码 8,896 行，但重点偏了

测试总量很可观（989 条），但从覆盖分布看：签名、schema、log、gate 这些「内部正确性」测得很深（90%+），而**对外接口和判据来源**（mcp_server / identity / mcp_probe / native）测得很浅（63–71%）。

也就是说：测试保护的是「我们没写错」，而不是「我们对外说的对不对」。

## 六、最该先做的三件

1. **C9 零余量**——改成 14 天过期，或加「快过期」告警。现在漏一次扫描就全盘失效。
2. **C11 静默失败**——原生摄取失败必须进 dead-letter，否则你永远不知道它是「上游没有」还是「我们坏了」。
3. **A3 + B7 说法**——数据集 README 必须警告假 pass；README 必须说清 gate 只是 1,437 个组件的白名单。

这三件都不需要新功能，只需要把「已经知道的事」说准、把「会静默坏的地方」变响。
